# 01. numpy 배치와 스레딩, GIL

## 요지

numpy는 대형 배열의 C 레벨 연산(ufunc, matmul, 슬라이스 복사) 동안 **GIL을 해제한다**.
무거운 배치를 워커 스레드로 빼도 메인(렌더) 루프는 막히지 않는다.
반대로 작은 연산을 수천 번 호출하면 매 호출마다 GIL을 잡아 메인 루프가 미세하게 끊긴다.

## 실측

- 20만 개 matmul 1회 = 12.9ms. 워커 스레드가 이걸 무한 반복하는 동안 메인 스레드 최악 지연은 **0.2~1.2ms**.
  GIL을 잡고 있었다면 ~13ms씩 멈췄을 것.
- 순수 파이썬 루프 워커는 메인을 꾸준히 **~5.3ms**씩 세운다 (GIL 스위치 간격 기본값 5ms).
- ThreadPool로 matmul 청크 분할: 1스레드 3.2ms → 2스레드 1.9 → 4스레드 1.1.
  GIL이 풀리므로 스레드로도 실제 멀티코어 스케일링이 나온다.

## 패턴

### 더블 버퍼링 — 락 없음

```python
front, back = buf_a, buf_b

def worker():
    global front, back
    while running:
        compute_into(back)          # 무거운 numpy 연산 (GIL 해제 구간)
        front, back = back, front   # 파이썬 참조 스왑은 원자적

# 메인 루프는 항상 front만 읽는다
```

- 읽기 공유는 락 없이 안전하다. 쓰기는 스레드마다 겹치지 않는 슬라이스로.
- 워커 루프에선 `np.matmul(A, B, out=buf)`처럼 출력 버퍼를 재사용한다.
  할당은 GIL을 잡는 파이썬 글루다.
- Queue로 결과 배열을 통째로 넘기는 것도 사실상 같은 패턴.

### 언제 스레드로 빼나

프로파일에서 프레임당 수 ms를 넘는 배치가 보일 때만.
10만 규모의 단순 산술(~0.1ms)은 싱글스레드로 끝이다.
진짜 병목은 대개 병렬화 부재가 아니라 **객체 단위 파이썬 루프** — SoA 전환이 항상 먼저다.

## GPU로 넘기는 기준

기준은 연산량이 아니라 **데이터가 어디 살아야 하는가**다.

| 데이터 | 위치 | 이유 |
|---|---|---|
| 로직이 결과를 읽음 (유닛, 총알, 충돌) | CPU | GPU readback이 더 비싸다 |
| 순수 시각용 (파티클) | GPU 상주 | pos+vel만 버퍼에 두고 셰이더에서 계산. 전송 0 |
| CPU 계산 + 렌더 (중간) | CPU, 업로드 최소화 | mat4(64B) 대신 pos+quat(32B)로 셰이더에서 조립 |

10만 × mat4를 매 프레임 업로드 = 6.4MB/frame ≈ 384MB/s @60fps. 가능하지만 낭비.

## 함정

- 함수 안에서 모듈 전역 배열에 `arr += x` → 증강 대입이 이름을 지역으로 재바인딩해 UnboundLocalError. `arr[:] += x`로 쓴다.
- 파이썬 3.11 기준. free-threaded 파이썬(3.13+)은 별개 논의.
