## 핵심 결정

1. 10만 규모는 CPU 싱글스레드 벡터화 numpy로 충분하다. 스레드/GPU 검토는 프로파일이 프레임당 수 ms짜리 배치를 보여줄 때만. → 01
2. GPU로 넘기는 기준은 연산량이 아니라 **데이터 상주**다. 로직이 읽어야 하는 데이터는 CPU에, 순수 시각용은 GPU 상주로. → 01
3. 트랜스폼은 **(N,4,4) float32 C-contiguous**. (N,16)은 같은 메모리의 뷰(reshape zero-copy)라 업로드 비용 차이가 없다. 합성은 matmul, 점 변환은 einsum. → 02
4. numpy는 대형 연산 중 GIL을 해제하므로 무거운 배치는 워커 스레드로 뺄 수 있다(더블 버퍼링). 더 필요하면 numba(parallel+nogil)로 matmul 대비 ~12배. → 01, 02
5. 오브젝트 로직은 3계층: **군중**(벡터화 FSM) / **스마트**(몸=배열, 뇌=파이썬 객체) / **소수**(그냥 파이썬). → 03
6. 군중의 상태 로직은 branchless 벡터화 FSM: 상태별 행동은 계수 테이블 조회, 전이는 마스크 쓰기. → 04

## 예산표 (실측, N=10만, 60fps 예산 16.6ms)

| 작업 | 프레임당 |
|---|---|
| `pos += vel*dt` 급 단순 산술 | ~0.1 ms |
| 4x4 배치 합성 `np.matmul` | 3.5~6 ms |
| 4x4 배치 합성 numba parallel | 0.3 ms |
| 파이썬 객체 `update()` 호출 1천 / 1만 / 10만 | 0.05 / 0.5 / 5.3 ms |
| 벡터화 FSM 풀 틱 (감각+전이+행동) | ~4 ms |
| 10만 일괄 조건검사 → 당첨 소수만 파이썬 | 0.03 ms |

## 규칙 한 줄씩

- 파이썬 루프는 전체 N이 아니라 **사건이 일어난 소수** 위에서만 돌린다 (`np.nonzero`).
- "골라서 연산"(fancy indexing 읽기-계산-쓰기)보다 "전부 연산하되 계수로 죽이기"가 빠르다.
- 벡터화 코드 비용 ≈ 풀스윕 횟수 × ~0.15ms (N=10만). 스윕 수를 센다.
- 최적화 순서: 벡터화(SoA) → 필요시 스레드/numba → 상주 문제일 때만 GPU.
- 함수 안에서 전역 배열에 `arr += x`는 UnboundLocalError. `arr[:] += x`로 쓴다.

## 측정 환경

py3.11 / numpy 2.4.6 / 4코어 컨테이너. 실행 간 편차가 있어 절대값보다 같은 런 안의 배율이 유효하다. 실제 타깃 머신에서 재측정할 것.
