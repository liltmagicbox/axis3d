# 지침 12. 계산은 CPU, GPU는 그리기 — 배치 결정 기준

> 선행: [지침 10](10-core-array.md), [11](11-kernels.md) · 관련 결정: D-013 · 원칙: 제6조

## 기본 자세

**GPU에 띄우기만 할 게 아니라면, 굳이 GPU로 계산하지 않는다.**

근거:

1. **왕복 비용.** 시뮬 결과를 게임 로직(충돌 판정, 이벤트)이 다시 읽어야 하는 순간 GPU→CPU 판독이 생기고, 그 동기화 지연이 계산 이득을 상쇄한다. N 수만~수십만 수준에서는 numpy CPU가 이미 프레임 예산 안이다 (10만 적분 ms급 — 실측 기반).
2. **아키텍처 비용.** 우리 시뮬은 headless 서버에서 도는 것이 기본 시나리오다 (제1조, 소켓 경계). 시뮬이 GPU를 요구하는 순간 서버 사양·배포·디버깅이 전부 무거워진다.
3. **도구 비용.** 파이썬 GPU 컴퓨트(CUDA/컴퓨트 셰이더/CuPy)는 디버깅·이식성·의존성 어느 쪽도 공짜가 아니다. 우리의 확장 카드는 [Numba](17-profiling-and-numba.md)가 먼저다 — 같은 코드 형태로 10~100배가 남아 있다.

## 그래도 GPU로 보내는 것

**로직이 결과를 읽을 필요가 없는 순수 시각 요소**는 애초에 시뮬레이션의 일이 아니다 — 뷰의 일이다.

- 장식용 파티클(불꽃, 연기, 시뮬에 영향 없는 눈): 뷰가 시드/파라미터만 받아 버텍스 셰이더에서 애니메이션. 시뮬은 "눈 내림 강도 0.7" 한 줄만 보낸다.
- 스키닝: 시뮬은 본 행렬만 계산·전송(6.4KB), 정점 변형은 뷰의 셰이더가 (600KB 정점 전송 금지 — test_renderer.py 실측 독백).
- 보간: 시뮬 20~60Hz 상태를 화면 주사율로 부드럽게 만드는 것은 뷰의 로컬 보간이다.

판별 질문 하나면 된다: **"이 계산 결과가 게임 상태에 영향을 주는가?"** 예 → CPU 시뮬. 아니오 → 뷰(=GPU)로 추방.

## 시뮬 계산의 GPU 이관을 검토해도 되는 조건 (전부 만족 시에만)

- [ ] N이 수백만 이상이고, Numba 승격 후에도 프레임 예산을 넘는다 (실측 첨부).
- [ ] 결과 판독이 없거나, 프레임당 판독량이 KB 수준으로 요약된다 (reduce 결과만 내려받기).
- [ ] 해당 계산이 다른 시스템과 데이터 의존이 없다 (파이프라인에서 섬처럼 분리 가능).
- [ ] headless 배포 요건을 포기하거나, CPU 폴백 경로를 유지할 수 있다.

체크리스트를 통과하면 decisions.md에 기록하고 진행한다. 통과 못 하면 그 계산은 Numba행이다.
